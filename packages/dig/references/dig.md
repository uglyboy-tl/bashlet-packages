# dig 站内检索指南

dig 是 research skill 自带的站内检索脚本（skill 目录下 `scripts/dig`）：在具体网站里搜它自己的
内容，而不是搜全网。被指派来跑 dig 时先读完本文件；下文命令里的 `dig` 都指这个脚本。

它只给你条目、不给结论；每个源的参数看 `dig <源> --help`。

## 一、每个源提供什么

源之间互不重叠（实测跨源重复率为 0）：每个源只对它自己的站点负责，增量各不相同。
判断一个源值不值得跑只有一条标准：**它能带来别处拿不到的增量吗？**——三个搜索引擎都索引过的 URL 不算增量。

跑哪几个由你按需要决定，只想要其中一项能力就只跑那一个源。下面按信息的性质分三层。

### 通用三源：技术话题的一手状态与主流讨论

| 源 | 独有的信息 | 什么时候别指望它 |
| --- | --- | --- |
| `github` | 某个库 / 工具**现在到底怎么样**：issue 与 PR 的 `state`、讨论、commit。`-T repos` 找项目、`-T code` 找实现、`-T commits` 找改动、`-T discussions` 找已经搬到 Discussions 的问答 | 纯概念 / 方法论问题——那里没有对应条目 |
| `hn` | 技术圈的公开观点与投票；`-T comments` 搜评论语料（「谁在哪条帖子下说过 X」） | 非技术话题；口味偏创业 / 前端 / 工具。`dig fetch <hn item 链接>`（`dig hn -u`）指向评论时返回的是那条评论本身，不是主帖；要主帖改用 `dig hn "<标题词>" -T stories -p all` |
| `so` | 「怎么做 X」的实操问答，以及多年沉淀的高赞答案（`-a` 取） | 开放式设计问题（会被关掉）；2023 年后的新事物（社区活跃度已降） |

### 按话题接：话题匹配时才有增量

| 源 | 独有的信息 | 什么时候别指望它 |
| --- | --- | --- |
| `discourse` | Python / PyTorch / Rust / OpenAI / HF / fly.io / Elastic 这些官方论坛里维护者的设计决定——比 SO 更接近一手 | 这些社区之外的话题 |
| `arxiv` | 预印本的摘要与作者 | 工程实操 |
| `openalex` | 被引数、会议期刊覆盖（比 arXiv 宽），摘要 | 没配 key 时容易限流 |
| `hf` | 模型 / 数据集的下载量与点赞（`-T datasets` 换数据集） | 不是 AI 话题 |
| `zhihu` | 中文一手讨论；热榜是「此刻中文互联网在讨论什么」的排序——这个排序 web 检索给不了 | 英文话题（搜不到） |
| `v2ex` | 中文技术圈的实际做法与吐槽；给主题链接能连回复一起取（`dig fetch`） | 非技术、非中文；本机直连不通，取主题要走云端浏览器 |
| `reddit` | 某个 subreddit 内的关键词搜索与最新帖；`-r` 一次拿**嵌套评论树**（免 key 走 Arctic Shift，不用代理） | 跨全站关键词搜索做不到（必须 `-s` 圈定社区）；同一 sub 的关键词搜索也会被上游限流，失败就隔一会儿重试或改用更短的词；有链接时优先 `dig fetch <帖子链接> -r N`（比关键词搜索稳） |
| `x` | 技术 / AI 话题的第一落点（HN 与 GitHub 常滞后几小时到几天）；人物与舆情的一手发言。已有链接时用 `dig x --tweet <id\|url>` 或 `dig fetch <链接>` 取单条（这条零凭证，长推文也给全文） | 需要 `X_AUTH_TOKEN` + `X_CT0`（取 queryId 用：F12 → Application → Cookies → `https://x.com` 复制 `auth_token` 与 `ct0`，两个值必须来自同一次登录会话）与代理；单页最多 20 条，热门词会漏 |

### 特定载体：只服务一类问题，别处拿不到

| 源 | 独有的信息 | 什么时候别指望它 |
| --- | --- | --- |
| `bilibili` | 中文视频的元数据、弹幕（免登录）、字幕全文稿（需 `BILI_SESSDATA`）。弹幕是**带时间轴的观众反应**，搜索引擎不索引弹幕全文 | 英文话题；没登录态时拿不到字幕 |
| `youtube` | 「有没有相关视频」、精确发布日期与简介、时长与播放量 | 字幕拿不到（见 §六） |
| `polymarket` | 真金白银的赔率与成交量 | 非预测类问题；无活跃市场时赔率没有信息量 |
| `wechat` | 公众号文章正文（**只能给链接取**，微信没有检索接口） | 需要「发现」时用 web 检索 |
| `weread` | 书目评分（0-1000）与在读人数；`-i N` 再补简介（判断值不值得读靠它） | 找书以外的一切场景 |

常见问法通常会用到哪几个，可作参考：

| 要回答的问题 | 通常是 |
| --- | --- |
| 这个库 / 工具能不能用、有没有坑 | `github -T issues` + `hn`（要看用法再加 `so -a 2`） |
| 这个方案该选哪个 | `hn` + `so` + `github -T repos`（看谁还在维护） |
| 这个方向研究到什么程度 | `arxiv` + `openalex` + `hn`（工程视角） |
| 中文圈怎么看这件事 | `zhihu` + `v2ex`（有视频再加 `bilibili -t`） |
| 某件事会不会发生 | `polymarket` + `hn` |
| 人物舆情 / 新闻 | `x` + web 检索（`x` 拿一手发言与现场反应，web 检索补时间线与背景；已有具体链接时见 §七） |

`dig doctor` 会逐个源列出状态（可达到 / 不可达 / 缺依赖 / 缺凭证）——空结果时先用它区分「真没有」和「源挂了」。

## 二、查询词按每个源自己的词汇习惯下

dig 是字面搜索，查询词决定一切。同一个话题在不同站点的说法不同：

- SO 上写 `bash array slice`，HN 上写 `Declare in Bash scripts`，GitHub issue 里写
  `slicing array indices`，Discourse 上写的是产品术语（`is_typeddict` 而不是「标题类型」）。
  **准备多个词，而不是一个词跑遍。**
- **中文话题用中文词搜中文源**（zhihu/v2ex/bilibili），英文源要用英文词。把中文词丢给
  hn/so/arxiv 会静默返回空——那不是「没人讨论」，是搜错了语言。
- **GitHub 要带限定符**：`repo:owner/name`、`is:issue`、`in:title`、`language:rust`。
  不带就只能拿全网同名项。
- Hugging Face 搜的是**模型名/任务名**（`bge-reranker`、`text-classification`），不是自然语言问句。

三类关键词陷阱（发现就换词）：

| 陷阱 | 例子 | 处理 |
| --- | --- | --- |
| 过泛的单字 | `bash`、`coffee` | 加锚点：`bash array slice` |
| 纯疑问句式 | `怎么用 Docker` | 站点上的真实用词是 `docker setup`、`docker production` |
| 数字碰撞 | `40 岁男人`、`the 100` | 数字会主导检索；除非它本身是话题（`GPT-4`），否则删掉 |

## 三、时间窗口：最容易搞错的一步

默认窗口是 `pastmonth`。**它只适合问「最近有什么新东西」，对「有哪些可用的东西」是错的**——
`repos` 的时间轴取「最后更新」（2018 年建的项目今天可能最活跃），`hf` / `openalex` 默认不筛时间
（下载量最大的往往不是今年出的）。这两条都是踩出来的，别退回默认值。

| 你要回答的问题 | 用什么窗口 |
| --- | --- |
| 最近发生了 / 大家在聊什么 | `-p pastmonth`（默认） |
| 一直以来怎么做、有哪些可用的东西 | `-p all` |
| 这个项目/库/模型还活着吗 | `-p pastmonth`（对 repos 是「最近还在更新」） |
| 论坛里有没有人踩过这个坑 | `-p all`（论坛的答案是长期资产） |

## 四、判读：哪条更硬、哪个数字会骗你

**热度不等于质量，来源不等于正确性，日子新不等于更相关。**

**各源里哪条更接近一手**

- **GitHub 要读 `state` 和它是不是 PR**：open 且最近有回复 = 事情正在发生；closed ≠ 不重要
  （可能是「已修复」，也可能是「不打算修」）；`is:pr` = 修复在途。
- **Discourse 是官方论坛**——维护者常在那里做设计决定，比 SO 更接近一手。
- **论文只看摘要判断不了影响力**：OpenAlex 的**被引数**才是这个方向热不热的信号。

**热度：不能跨源比，也不能代替阅读**

| 源 | 数字是什么 | 会误导你的地方 |
| --- | --- | --- |
| `hn` | points = 是否上了首页 | 高分是「吸引眼球」，不是「说得对」 |
| `so` | score = 多年累计的「有用」 | 高分答案常常是十年前的 |
| `github` | comments / stars | stars 是历史积累，不反映现在是否可用 |
| `hf` | downloads / likes | 下载量含 CI 与爬虫；likes 才是人的动作 |
| `bilibili` | 播放 / 弹幕 / 评论 | 播放量有推广水分，弹幕更接近真实反应 |
| `zhihu` | 赞同 / 评论 | 赞同是情绪与立场的产物 |
| `v2ex` | replies | 回复多不等于说得对；热帖回复里常见跑题与站务吐 |
| `discourse` | replies / views / likes | views 含爬虫与回访，replies 才是人的动作 |
| `youtube` | views / duration / age | 播放量有推广水分；`age` 是「3 年前」这种粗粒度文本，要精确日期用 `-t` |
| `weread` | rating（0-1000，930 = 93.0） | 只在微信读书读者里抽样 |
| `polymarket` | volume / liquidity | 成交量低的市场，赔率没有信息量 |

**做法：用数字挑候选，用 `text` 下判断。** 至少读前几条正文再决定它值不值得写进结论。

问答站尤其要开 `-a`：**SO 真正值钱的是答案，不是问题**。不开只会拿到提问者的描述，而高分答案
（尤其「已采纳」那个）才是经过多年投票的结果。

**时间**：见第三节。另外，`created_at` 为空的条目（微信读书书目、知乎热榜、Polymarket）
只能当背景，不能当「新动向」。

**dig 不做跨源融合**：各源结果分开给你，印证与重复由你自己看。

## 五、空结果先排除三种假空

按顺序排除：窗口太短 → 查询词太窄或语言错 → 源挂了（看 `dig doctor`）。都排除不了才是
「真的没有」——饱和就停（换新词后回到看过的标题 / URL），不要用 web 检索的内容填 dig 的空洞。

## 六、dig 自己的边界（别向用户承诺这些）

| 拿不到 / 不全 | 怎么办 |
| --- | --- |
| 公众号检索 | 微信没有公开检索接口：发现用 web 检索，拿到链接再 `dig fetch <url>` |
| 知乎回答正文 | 开放平台只给搜索、热榜与摘要——用它挑候选，正文拿不到 |
| B 站字幕 | 要配 `BILI_SESSDATA` 才有：`dig bilibili "词" -t N` |
| B 站弹幕 | 只有抽样，够看观众在反应什么，不够做量化 |
| YouTube 字幕 / 转写 | 拿不到（结构性的，别重试）；`dig youtube -t N` 给发布日期与简介 |
| Reddit 跨全站搜索 | 必须圈定社区：`dig reddit -s <sub> "词"` |

失败要当失败报：源挂了就直说「不可达 / 缺凭证」，不要说成「没搜到」。

页面取不回时，见下节。

## 七、已经有链接时：`dig fetch <url>`

检索是「手上没有 URL、去源里找」。**已经有链接、但普通抓取拿不回正文**时，只有落在 dig 有源的那类站点上才轮到它——
技术社区 / 论文 / 代码仓与模型库 / 视频 / 预测市场；`dig fetch <url>` 把这一条取全，输出与检索结果同形。
其余站点（博客、新闻、PDF）不归它管——报「认不出」就换等价信源，不要绕着试。
页面里本来就有的字段也不必转这一道——增量是「字段在 API 里」（如 B 站字幕与弹幕）、结构化字段、批量取。

```bash
dig fetch https://arxiv.org/abs/1706.03762           # 论文：摘要
dig fetch <reddit 帖子链接> -r 3                     # 帖子 + 3 层评论树
```

- **URL 必须是第一个实参**，之后的选项原样转给那个源（`-r 3`、`--no-cache` 都能用）。
- 环境里配了云端浏览器、且开了 `DIG_FETCH_FALLBACK=1` 时，认不出的 URL 也会兜底取一页；**默认关**。

## 八、入口

```bash
dig doctor                  # 探活：哪些源可用、缺什么
dig hn "query"              # 取数；默认每条带一行正文预览，--json 看完整正文，-o 落盘
dig fetch <url>             # 已有链接：判断属于哪个源并取这一条（URL 后的选项转给该源）
dig <源> --help             # 该源的特有参数（github -T、hn -T/-c、bilibili -t/-d、so -s…）
```

同一个查询（源 + 词 + 条数 + 窗口 + 该源参数）一天内重复跑会直接回放本地结果缓存，命中时 stderr 打一行 INFO；
要最新数据加 `--no-cache`。
