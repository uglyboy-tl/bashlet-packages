# dig 站内检索

dig 是一个站内检索脚本:在具体网站里搜它自己的内容,而不是搜全网;也是常规抓取拿不回正文时的兜底通道。它只给你条目、不给结论。下文命令里的 `dig` 都指这个脚本。

脚本在本技能目录的 `scripts/dig`,**不在 PATH 里**;凭据与源开关在 `scripts/.env`(与脚本同目录)。

## 什么时候用

- 已经知道去哪个站找,或要「这个站里怎么说」。
- 已有链接、常规抓取拿不回正文,且落在它支持的站点上(见〈已经有链接时〉)。

dig 只认〈每个源〉里列出的站点类型:不认的页面(博客、新闻、PDF)会报「认不出」——这是它的边界,绕不过去。

## 跑哪几个源

一条判据:**它能带来别处拿不到的增量吗?**——三个搜索引擎都索引过的 URL 不算增量。源之间互不重叠(实测跨源重复率为 0),所以跑哪几个由你按子问题决定,只想要其中一项能力就只跑那一个源。

选源先问「谁会讨论这件事」:官方维护者常在 Discourse 与 GitHub issue,实践者在 SO / HN / reddit / v2ex,中文圈在 zhihu / v2ex / bilibili,一手载体另算(arxiv / polymarket / x)。

常见问法通常会用到哪几个:

| 要回答的问题 | 通常是 |
| --- | --- |
| 这个库 / 工具能不能用、有没有坑 | `github -T issues` + `hn`(要看用法再加 `so -a 2`) |
| 这个方案该选哪个 | `hn` + `so` + `github -T repos`(看谁还在维护) |
| 这个方向研究到什么程度 | `arxiv` + `openalex` + `hn`(工程视角) |
| 中文圈怎么看这件事 | `zhihu` + `v2ex`(有视频再加 `bilibili -t`) |
| 某件事会不会发生 | `polymarket` + `hn` |
| 人物舆情 / 新闻 | `x`(`x` 拿一手发言与现场反应;时间线与背景靠别的信源补。已有具体链接时见〈已经有链接时〉) |

## 每个源:增量 / 盲区 / 专有参数

### 通用三源:技术话题的一手状态与主流讨论

| 源 | 独有的增量 | 什么时候别指望它 | 专有参数与坑 |
| --- | --- | --- | --- |
| `github` | 某个库 / 工具**现在到底怎么样**:issue 与 PR 的 `state`、讨论、commit | 纯概念 / 方法论问题——那里没有对应条目 | `-T repos` 找项目、`-T code` 找实现、`-T commits` 找改动、`-T discussions` 找已搬到 Discussions 的问答;查询要带限定符(`repo:owner/name`、`is:issue`、`in:title`、`language:rust`),不带就只拿全网同名项 |
| `hn` | 技术圈的公开观点与投票 | 非技术话题;口味偏创业 / 前端 / 工具 | `-T comments` 搜评论语料(「谁在哪条帖子下说过 X」)、`-T stories` 搜帖子;`-c N` 抓故事评论树;`-u` / `dig fetch` 指向评论时返回的是**那条评论**而非主帖,要主帖用 `-T stories "<标题词>" -p all` |
| `so` | 「怎么做 X」的实操问答,以及多年沉淀的高赞答案 | 开放式设计问题(会被关掉);2023 年后的新事物(社区活跃度已降) | **`-a N` 抓高赞答案填进 `text`**——SO 真正值钱的是答案不是问题;`-s` 换 StackExchange 站点 |

### 按话题接:话题匹配时才有增量

| 源 | 独有的增量 | 什么时候别指望它 | 专有参数与坑 |
| --- | --- | --- | --- |
| `discourse` | Python / PyTorch / Rust / OpenAI / HF / fly.io / Elastic 官方论坛里维护者的设计决定——比 SO 更接近一手 | 这些社区之外的话题 | 无特殊参数;`-s <host>` 换社区(默认 Python / PyTorch / Rust / OpenAI / HF / fly.io / Elastic / meta.discourse.org 八个) |
| `arxiv` | 预印本的摘要与作者 | 工程实操 | 无 |
| `openalex` | 被引数、会议期刊覆盖(比 arXiv 宽),摘要 | 没配 key 时容易限流 | 无 |
| `hf` | 模型 / 数据集的下载量与点赞 | 不是 AI 话题 | `-T datasets` 换数据集;搜的是**模型名 / 任务名**(`bge-reranker`、`text-classification`),不是自然语言问句 |
| `zhihu` | 中文一手讨论;热榜是「此刻中文互联网在讨论什么」的排序 | 英文话题(搜不到);**正文拿不到**(开放平台只给搜索、热榜与摘要) | 用中文词;摘要是候选筛选手段,引用只能停在标题/摘要级 |
| `v2ex` | 中文技术圈的实际做法与吐槽;给主题链接能连回复一起取 | 非技术、非中文;本机直连不通时,取主题要走云端浏览器 | 发现用关键词检索,取正文用 `dig fetch <主题链接>` |
| `reddit` | 某个 subreddit 内的关键词搜索与最新帖;`-r` 一次拿**嵌套评论树** | 跨全站关键词搜索做不到(必须圈定社区) | **`-s <sub>` 必给**;**关键词搜索被上游限流很常见(连续调用会 422 超时)——发现这一步别走它:拿到帖子链接后 `dig fetch <链接> -r N`,这条最稳**;一次失败别连着重试 |
| `x` | 技术 / AI 话题的第一落点(HN 与 GitHub 常滞后几小时到几天);人物与舆情的一手发言 | 单页最多 20 条,热门词会漏 | 需要 `X_AUTH_TOKEN` + `X_CT0`(F12 → Application → Cookies → `https://x.com` 复制 `auth_token` 与 `ct0`,两个值必须来自同一次登录会话)与代理;`--tweet <id\|url>` 或 `dig fetch <链接>` 取单条**零凭证**,长推文也给全文 |

### 特定载体:只服务一类问题,别处拿不到

| 源 | 独有的增量 | 什么时候别指望它 | 专有参数与坑 |
| --- | --- | --- | --- |
| `bilibili` | 中文视频的元数据、弹幕(免登录)、字幕全文稿。弹幕是**带时间轴的观众反应**,搜索引擎不索引弹幕全文 | 英文话题;没登录态时拿不到字幕 | `-t N` 取字幕全文稿(需配 `BILI_SESSDATA`)、`-d` 取弹幕(只有抽样,够看观众在反应什么,不够做量化) |
| `youtube` | 「有没有相关视频」、精确发布日期与简介、时长与播放量 | **字幕 / 转写拿不到**(结构性的,别重试) | `-t N` 补精确发布日期与简介;`age` 字段是「3 年前」这种粗粒度文本 |
| `polymarket` | 真金白银的赔率与成交量 | 非预测类问题;无活跃市场时赔率没有信息量 | 无 |
| `wechat` | 公众号文章正文 | 微信**没有检索接口**:只能给链接取,不能发现 | `dig fetch <链接>` |
| `weread` | 书目评分(0-1000)与在读人数 | 找书以外的一切场景 | `-i N` 再补简介(判断值不值得读靠它) |

## 下查询词

dig 是字面搜索,查询词决定一切。同一个话题在不同站点的说法不同:

- SO 上写 `bash array slice`,HN 上写 `Declare in Bash scripts`,GitHub issue 里写 `slicing array indices`,Discourse 上写的是产品术语(`is_typeddict` 而不是「标题类型」)。**准备多个词,而不是一个词跑遍。**
- **中文话题用中文词搜中文源**(zhihu/v2ex/bilibili),英文源要用英文词。把中文词丢给 hn/so/arxiv 会静默返回空——那不是「没人讨论」,是搜错了语言。

三类关键词陷阱(发现就换词):

| 陷阱 | 例子 | 处理 |
| --- | --- | --- |
| 过泛的单字 | `bash`、`coffee` | 加锚点:`bash array slice` |
| 纯疑问句式 | `怎么用 Docker` | 站点上的真实用词是 `docker setup`、`docker production` |
| 数字碰撞 | `40 岁男人`、`the 100` | 数字会主导检索;除非它本身是话题(`GPT-4`),否则删掉 |

## 选时间窗口

**默认窗口是 `pastmonth`,而 `--help` 不显示这件事。** 它只适合问「最近有什么新东西」,对「有哪些可用的东西」是错的:问答与社区类源(so / hn / zhihu / v2ex / reddit)的默认窗口只回最近一个月,**十年前那个高分答案看不见**——空结果会被误读成「没人说过」。这两条都是实测踩出来的。

| 你要回答的问题 | 用什么窗口 |
| --- | --- |
| 最近发生了 / 大家在聊什么 | `-p pastmonth`(默认) |
| 一直以来怎么做、有哪些可用的东西 / 成熟做法 | `-p all`(默认值在这里几乎总是错的) |
| 这个项目/库/模型还活着吗 | `-p pastmonth`(对 `repos` 是「最近还在更新」;2018 年建的项目今天可能最活跃) |
| 论坛里有没有人踩过这个坑 | `-p all`(论坛的答案是长期资产) |

`hf` / `openalex` 默认不筛时间(下载量最大的往往不是今年出的),不要用窗口去「找新的」。

## 怎么跑

```bash
<本技能目录>/scripts/dig doctor          # 探活:逐个源列出可达 / 不可达 / 缺依赖 / 缺凭证
<本技能目录>/scripts/dig hn "query"      # 检索;默认每条带一行正文预览
<本技能目录>/scripts/dig fetch <url>     # 已有链接:判断属于哪个源并取这一条(URL 后的选项转给该源)
<本技能目录>/scripts/dig <源> --help     # 该源的特有参数(github -T、hn -T/-c、bilibili -t/-d、so -s…)
```

- 要引用原文(引用句、数字、日期)就加 `--json` 拿完整正文,或用 `-o <file>` 落盘;人类可读形态每条只给一行预览。
- 同一个查询(源 + 词 + 条数 + 窗口 + 该源参数)一天内重复跑会直接回放本地结果缓存,命中时 stderr 打一行 INFO;要最新数据加 `--no-cache`。

## 已经有链接时:`dig fetch <url>`

检索是「手上没有 URL、去源里找」。**已经有链接、但普通抓取拿不回正文**时,只有落在 dig 有源的那类站点上才轮到它——技术社区 / 论文 / 代码仓与模型库 / 视频 / 预测市场;`dig fetch <url>` 把这一条取全,输出与检索结果同形。其余站点(博客、新闻、PDF)不归它管——报「认不出」就换等价信源,不要绕着试。页面里本来就有的字段也不必转这一道——增量是「字段在 API 里」(如 B 站字幕与弹幕)、结构化字段、批量取。

```bash
dig fetch https://arxiv.org/abs/1706.03762           # 论文:摘要
dig fetch <reddit 帖子链接> -r 3                     # 帖子 + 3 层评论树
```

- **URL 必须是第一个实参**,之后的选项原样转给那个源(`-r 3`、`--no-cache` 都能用)。
- **环境里配了云端浏览器凭证**、且开了 `DIG_FETCH_FALLBACK=1` 时,认不出的 URL 也会兜底取一页;**默认关**。

## 读结果

**热度不等于质量,来源不等于正确性,日子新不等于更相关。**

各源里哪条更接近一手:

- **GitHub 要读 `state` 和它是不是 PR**:open 且最近有回复 = 事情正在发生;closed ≠ 不重要(可能是「已修复」,也可能是「不打算修」);`is:pr` = 修复在途。
- **Discourse 是官方论坛**——维护者常在那里做设计决定,比 SO 更接近一手。
- **论文只看摘要判断不了影响力**:OpenAlex 的**被引数**才是这个方向热不热的信号。

数字是什么、会怎么误导你:

| 源 | 数字是什么 | 会误导你的地方 |
| --- | --- | --- |
| `hn` | points = 是否上了首页 | 高分是「吸引眼球」,不是「说得对」 |
| `so` | score = 多年累计的「有用」 | 高分答案常常是十年前的 |
| `github` | comments / stars | stars 是历史积累,不反映现在是否可用 |
| `hf` | downloads / likes | 下载量含 CI 与爬虫;likes 才是人的动作 |
| `bilibili` | 播放 / 弹幕 / 评论 | 播放量有推广水分,弹幕更接近真实反应 |
| `zhihu` | 赞同 / 评论 | 赞同是情绪与立场的产物 |
| `v2ex` | replies | 回复多不等于说得对;热帖回复里常见跑题与站务吐 |
| `discourse` | replies / views / likes | views 含爬虫与回访,replies 才是人的动作 |
| `youtube` | views / duration / age | 播放量有推广水分 |
| `weread` | rating(0-1000,930 = 93.0) | 只在微信读书读者里抽样 |
| `polymarket` | volume / liquidity | 成交量低的市场,赔率没有信息量 |

**做法:用数字挑候选,用 `text` 下判断。** 至少读前几条正文再决定它值不值得写进结论。

`created_at` 为空的条目(微信读书书目、知乎热榜、Polymarket)只能当背景,不能当「新动向」。dig **不做跨源融合**:各源结果分开给你,印证与重复由你自己看。

## 结果为空时

按顺序排除三种假空:**窗口太短**(见〈选时间窗口〉——问「有哪些 / 成熟做法」没加 `-p all` 是第一嫌疑)→ **查询词太窄或语言错**(见〈下查询词〉)→ **源挂了**(看 `dig doctor`)。都排除不了才是「真的没有」——饱和就停(换新词后回到看过的标题 / URL);是空就报空。

## 别向用户承诺这些

| 拿不到 / 不全 | 怎么办 |
| --- | --- |
| 公众号检索 | 微信没有公开检索接口:发现要靠别的信源,拿到链接再 `dig fetch <url>` |
| 知乎回答正文 | 开放平台只给搜索、热榜与摘要——用它挑候选,正文拿不到 |
| B 站字幕 | 要配 `BILI_SESSDATA` 才有:`dig bilibili "词" -t N` |
| B 站弹幕 | 只有抽样,够看观众在反应什么,不够做量化 |
| YouTube 字幕 / 转写 | 拿不到(结构性的,别重试);`dig youtube -t N` 给发布日期与简介 |
| Reddit 跨全站搜索 | 必须圈定社区:`dig reddit -s <sub> "词"` |

失败要当失败报:源挂了就直说「不可达 / 缺凭证」,不要说成「没搜到」。页面取不回时见〈已经有链接时〉。
