# dig

dig 从**具体站点**取数：HN 的投票与评论、GitHub 的一手状态、SO 多年沉淀的问答、Discourse
官方论坛的讨论、论文的被引数、Hugging Face 的模型下载量、B 站弹幕与字幕、Polymarket 的赔率。

它**不给你结论**，只给你条目。这个文件讲三件事：**去哪找**、**怎么下词**、**怎么判断值不值**。

选项、凭证、schema 细节一律看 `dig <子命令> --help` 与 `dig sources`，本文件不重复。

## 一、先决定跑哪几个源——**默认只跑 1-2 个**

dig 不是聚合器。**一次调研跑 2-4 个源是常态，跑满 13 个是错的**：源越多，噪声越多，判断越被稀释。

`dig sources` 会把 13 个源按重要性分成三层（这个分级是机器可读的，不是本文档的口头约定）：

### 核心层：几乎每次调研都该跑

| 源 | 什么时候用 | 什么时候别用 |
| --- | --- | --- |
| `github` | 任何涉及「某个库 / 工具 / 项目**现在到底怎么样**」的调研——一手状态；`-T repos/code/commits/discussions` 分别找项目、找实现、找改动、找 **Discussions**（很多项目已经把 Q&A 从 issue 搬到了那里） | 纯概念 / 方法论问题（那里没有对应的 issue） |
| `hn` | 技术选型、踩坑、行业观点；`-T comments` 直接搜「谁说过 X」 | 非技术话题；HN 的口味偏创业 / 前端 / 工具 |
| `so` | 「**怎么做** X」的实操问题，`-a` 取高赞答案 | 开放式设计问题（会被关掉）；2023 年后的新事物（SO 活跃度已降） |

### 按话题选：只在匹配的话题类型上用

| 源 | 什么时候用 | 什么时候别用 |
| --- | --- | --- |
| `discourse` | 话题属于 **Python / PyTorch / Rust / OpenAI / HF / fly.io / Elastic** 这些生态时，**优先于 SO**——官方论坛里有维护者的设计决定 | 这些社区之外的话题 |
| `arxiv` | 研究方法、方向综述 | 工程实操 |
| `openalex` | 需要**被引数**或会议期刊覆盖 | 没配 key 时容易限流空手而归；预印本用 arxiv 更快 |
| `zhihu` | **中文**话题的一手讨论与热榜 | 英文话题（搜不到） |
| `v2ex` | 中文技术圈的实际做法与吐槽 | 非技术、非中文 |
| `hf` | **AI 话题**里要选模型 / 数据集 | 不是 AI 话题 |

### 特定场景：极少用，但用了不可替代

| 源 | 什么时候用 | 什么时候别用 |
| --- | --- | --- |
| `bilibili` | 答案可能是**中文视频 / 教程**，或要看观众反应 | 没设 `BILI_SESSDATA` 时只有元数据 + 弹幕，价值有限；英文话题 |
| `youtube` | 只想确认「有没有相关视频」 | **字幕拿不到**，别指望从它提取知识 |
| `polymarket` | 问题本质是「**某事会不会发生**」 | 非预测类问题；无活跃市场（赔率无信息量） |
| `weread` | 找书 / 判断一本书值不值得读 | 其他一切场景 |

### 几个成型的组合

| 要回答的问题 | 跑什么 |
| --- | --- |
| 这个库/工具能不能用、有没有坑 | `github -T issues` + `hn`（+ `so -a 2` 如果要看用法） |
| 这个方案该选哪个 | `hn` + `so` + `github -T repos`（看谁还在维护） |
| 这个方向研究到什么程度 | `arxiv` + `openalex` + `hn`（工程视角） |
| 中文圈怎么看这件事 | `zhihu` + `v2ex`（+ `bilibili -t` 若有视频） |
| 某件事会不会发生 / 市场怎么看 | `polymarket` + `hn` |
| 人物舆情 / 新闻 / 读某篇原文 | **不是 dig 的活**，用你自己的 web 检索 |

判断一个源值不值得跑，只有一条标准：**它能带来别处拿不到的增量吗？** 同一个 URL 三个搜索引擎
都索引过的内容不是增量。

`dig doctor` 每个会话跑一次：它告诉你当前网络/凭证下哪些源可用。此后再遇到空结果，你才能确定
是「真没有」而不是「源挂了」。

## 二、查询词按每个源自己的词汇习惯下

dig 是字面搜索，查询词决定一切。同一个话题在不同站点的说法不同：

- SO 上写 `bash array slice`，HN 上写 `Declare in Bash scripts`，GitHub issue 里写
  `slicing array indices`，Discourse 上写的是产品术语（`is_typeddict` 而不是「标题类型」）。
  **准备多个词，而不是一个词跑遍。**
- **中文话题用中文词搜中文源**（zhihu/v2ex/bilibili），英文源要用英文词。把中文词丢给
  hn/so/arxiv 会静默返回空——那不是「没人讨论」，是搜错了语言。
- **GitHub 要带限定符**：`repo:owner/name`、`is:issue`、`in:title`、`language:rust`。
  不带就只能拿全网同名项。
- Hugging Face 搜的是**模型名/任务名**（`bge-reranker`、`text-classification`），不是自然语言问句。

四类关键词陷阱（发现就换词）：

| 陷阱 | 例子 | 处理 |
| --- | --- | --- |
| 过泛的单字 | `bash`、`coffee` | 加锚点：`bash array slice` |
| 纯疑问句式 | `怎么用 Docker` | 站点上的真实用词是 `docker setup`、`docker production` |
| 数字碰撞 | `40 岁男人`、`the 100` | 数字会主导检索；除非它本身是话题（`GPT-4`），否则删掉 |
| 跨语言 | 中文词搜英文源 | 换语言；两边都搜过再下「没有」的结论 |

## 三、时间窗口：最容易搞错的一步

默认窗口是 `pastmonth`。**它只适合问「最近有什么新东西」，对「有哪些可用的东西」是错的。**
这一条是本项目自己踩出来的：

- `dig github "..." -T repos` 默认窗口返回空——仓库的创建时间不是有用的时间轴，一个 2018 年建的
  项目今天最活跃。所以 repos 模式的时间轴取**最后更新**。
- `dig hf "reranker"` 默认窗口返回空——2024 年的模型下载量最多，却全被滤掉。所以 hf / openalex
  **默认不筛时间**。

| 你要回答的问题 | 用什么窗口 |
| --- | --- |
| 最近发生了 / 大家在聊什么 | `-p pastmonth`（默认） |
| 一直以来怎么做、有哪些可用的东西 | `-p all` |
| 这个项目/库/模型还活着吗 | `-p pastmonth`（对 repos 是「最近还在更新」） |
| 论坛里有没有人踩过这个坑 | `-p all`（论坛的答案是长期资产） |

**空结果永远先怀疑窗口，再怀疑查询词，最后才怀疑源坏了。**

## 四、判读：来源、热度、时间，三件事分开看

**热度不等于质量，来源不等于正确性，日子新不等于更相关。**

**来源：一手 > 二手 > 三手**

- 维护者在 issue / PR 里的回复、commit、release note = 一手。
- 使用者在 SO / HN / 论坛的回答 = 二手经验（可能只对他自己的环境成立）。
- 列表文、聚合站、二手转述 = 三手。
- **GitHub 要读 `state` 和它是不是 PR**：open 且最近有回复 = 事情正在发生；closed ≠ 不重要
  （可能是「已修复」，也可能是「不打算修」）；`is:pr` = 修复在途。
- **Discourse 的「官方论坛」回答带官方色彩**——维护者常在那里做设计决定，比 SO 更接近一手。
- 论文只看摘要：它不告诉你这个方向是否热门、是否被推翻；OpenAlex 的**被引数**才是影响力信号。

**热度：不能跨源比，也不能代替阅读**

| 源 | 数字是什么 | 会误导你的地方 |
| --- | --- | --- |
| `hn` | points = 是否上了首页 | 高分是「吸引眼球」，不是「说得对」 |
| `so` | score = 多年累计的「有用」 | 高分答案常常是十年前的 |
| `github` | comments / stars | stars 是历史积累，不反映现在是否可用 |
| `hf` | downloads / likes | 下载量含 CI 与爬虫；likes 才是人的动作 |
| `bilibili` | 播放 / 弹幕 / 评论 | 播放量有推广水分，弹幕更接近真实反应 |
| `zhihu` | 赞同 / 评论 | 赞同是情绪与立场的产物 |
| `weread` | rating（0-1000，930 = 93.0） | 只在微信读书读者里抽样 |
| `polymarket` | volume / liquidity | 成交量低的市场，赔率没有信息量 |

**做法：用数字挑候选，用 `text` 下判断。** 至少读前几条正文再决定它值不值得写进结论。

问答站尤其要开 `-a`：**SO 真正值钱的是答案，不是问题**。不开只会拿到提问者的描述，而高分答案
（尤其「已采纳」那个）才是经过多年投票的结果。

**时间**：见第三节。另外，`created_at` 为空的条目（微信读书书目、知乎热榜、Polymarket）
只能当背景，不能当「新动向」。

**交叉确认 vs 单一来源**：同一个说法在 HN 和 SO 各自独立出现 = 交叉确认；同一个 URL 或同一作者
在不同源重复 = 单一来源。dig 不做跨源融合，正是为了不掩盖这件事。

## 五、什么时候停，以及怎么诚实地说「没找到」

- **饱和就停**：换新词后回到你已经看过的标题 / URL。
- **空结果也是结果**，但先排除三种假空：源报错（看 `dig doctor`）、查询太窄或语言错、窗口太短。
- **不要用 web 检索的内容去填 dig 的空洞**，也不要用它假装 dig 的结果。
- 结论里每条关键判断都要能追到 `source` + `url`（+ 时间）。给不出来就别写成结论。

## 六、已知限制（不要向用户承诺这些）

| 想要的 | 能不能拿到 | 替代 |
| --- | --- | --- |
| **B 站字幕** | ⚠️ 匿名拿不到，**带 `BILI_SESSDATA` 就能拿**（实测 0/10 → 10/10） | `dig bilibili "词" -t N` |
| B 站弹幕 | ✅ 免登录 | `dig bilibili "词" -d N` |
| YouTube 字幕 / 转写 | ❌ 出口 IP 被封（timedtext 恒空、get_transcript 400）；加任何 cookie/header 都无效，住户代理也没用 | `dig youtube -t N` 给发布日期 + 简介 |
| Reddit | ❌ 匿名 `.json` 全部 403；PullPush 免 cookie 但实测连续 429 | 用 `hn` + `v2ex` + `discourse` 补社区讨论 |
| X / Twitter | ❌ 未接线（搜索要 cookie + 会轮换的 queryId）；零凭证只能读**已知推文 ID**，不能搜 | 技术/AI 话题用 `hn` + `huggingface` + GitHub 补；完整方案见 `docs/candidates.md` |
| Lobsters | ❌ Anubis 人机验证（要跑 JS 解 PoW） | `hn` |
| 小红书 / 微博 / X | ❌ 卡在 JS 签名（`x-s`/`x-t`）或登录态 | — |
| 知乎任意用户主页 / 全量回答 | ❌ 官方开放平台只给搜索/热榜/本人内容 | — |
| Invidious / Piped（第三方 YouTube 前端） | ❌ 全部实例 DNS 能解析但连不上（直连与代理都是 000） | 不依赖第三方，用 `dig youtube` |

失败要当失败报：源挂了就直说「不可达 / 缺凭证」，不要说成「没搜到」。

## 七、入口

```bash
dig doctor                  # 会话开始时跑一次：哪些源现在可用（含代理是否生效）
dig sources                 # 每个源的说明 / 凭证 / 依赖 / 能力
dig hn "query"              # 取数；--json 出 JSONL，-o 落盘
dig <源> --help             # 该源的特有参数（github -T、hn -T/-c、bilibili -t/-d、so -s…）
```

代理：`DIG_PROXY` 环境变量 > `~/.config/dig/config.toml` 的 `proxy.url` > `https_proxy`。
登录态：目前只有 B 站字幕需要，用 `BILI_SESSDATA` 环境变量（dig 不抓浏览器 cookie）。

多源结果各写一份文件，按 `source` 字段分别读——dig 不提供跨源合并排名，那一步判断归你。
